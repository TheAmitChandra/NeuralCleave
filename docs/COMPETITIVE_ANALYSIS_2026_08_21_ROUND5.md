## 4. Round-4 wiring re-verification

Applying Round 4 §7's own stated lesson ("grep for every call site that constructs a gated object and confirm at least one of them can actually pass a non-default value in the live gateway path") to Round 4's own deliverables:

### 4.1 `[security]` config → `POLICY` → `ToolRegistry` → `ShellTool`/`BrowserAutomationTool` — **PASS**
Traced end-to-end: `config.py:99-135` defines `SecurityConfig` (`require_shell_approval: bool = False`, `security_mode`, `ask_mode`), parsed at `config.py:306-308`. `agent/runtime.py:175-183` (`AgentRuntime.from_config()`) sets `POLICY.security`/`.ask` from config and calls `ToolRegistry.default(require_approval=cfg.security.require_shell_approval)`. `tools/registry.py:190-192` passes that straight into `ShellTool(require_approval=...)` and `BrowserAutomationTool(require_approval=...)`, which store it as `self._require_approval` (`tools/shell.py:141`, `tools/browser.py:430`) and gate on it at the real call site (`tools/shell.py:181`, `tools/browser.py:451`). A real `config.toml` with `require_shell_approval = true` genuinely reaches and gates the live tool.

### 4.2 `ApprovalQueue.on_request` → `AgentRuntime._handle_new_approval_request` → `notify_channel` — **PASS**
`agent/runtime.py:150` wires `APPROVAL_QUEUE.on_request = self._handle_new_approval_request` in the constructor (so every `AgentRuntime` instance, including the one built by `_init_runtime()` in the live gateway, has this hook live). `_handle_new_approval_request` (`runtime.py:906-927`) resolves the real session/adapter and schedules `_notify_and_record` (`runtime.py:929-933`), which awaits `notify_channel(...)` and increments `approval_notifications_total` via the real `REGISTRY.inc(...)` call — not a mock, the same counter object the Prometheus endpoint exposes. This is a live-path increment, not a test-only one.

### 4.3 `/think` ladder for Ollama/DeepSeek — **PASS for the non-streaming path, but with a real depth gap Round 4 didn't check**
`models/thinking.py` is honestly scoped and well-documented: it maps Anthropic/xAI/OpenRouter/Ollama, and explicitly declines DeepSeek with a documented rationale (DeepSeek's API has no per-request reasoning field at all — only a model-choice lever the user already controls). That part of Round 4's claim is solid.

**New finding**: `ModelRouter.generate()` (`models/router.py:352-437`) accepts and correctly threads a `thinking` parameter through to `_call()` (`router.py:620-720`), which applies `resolve_thinking_params(...)` per-provider. But `ModelRouter.generate_stream()` (`router.py:469-525`) has **no `thinking` parameter in its signature at all**, and its own docstring says so outright: *"Extended thinking is not supported in the streaming path."* `_call_stream()` (`router.py:527-618`) likewise has no `thinking`/`reasoning_effort`/`think` kwarg anywhere in its dispatch to any provider's `_xxx_stream()` method.

This matters because of *which* live paths use which method. Tracing actual callers:
- **External channel adapters** (Telegram, Slack, Discord, and the other ~29) go through `_on_message` → `_reply_for()` (`runtime.py:368-372,812-860`) → `CognitivePipeline.run()` (`pipeline.py:140-224`) → `router.generate()` — **thinking is applied.**
- **The Web UI chat** (`gateway/websocket.py:204,326,401`) and **the voice assistant** (`agent/runtime.py:451`, `_on_voice_transcription`) both go through `process_inbound_text_stream()` → `CognitivePipeline.run_stream()` (`pipeline.py:226-299`) → `router.generate_stream()` — **thinking is silently dropped**, structurally, regardless of what `/think` level is set (the level lives on `router._thinking_level`, set via the `/think` slash command at `runtime.py:1068` or the REST route at `routes.py:873-876`, and is shared across both code paths — only one of them ever reads it).

So the `/think` ladder built across Rounds 3-4 works for every third-party channel and silently no-ops for NeuralCleave's own native Web UI and voice surfaces — arguably backwards from what a user would expect. No test anywhere exercises `generate_stream(thinking=...)` (confirmed via grep — zero matches), consistent with this being a genuinely undiscovered gap rather than a known, accepted limitation.

### 4.4 `/ready`'s runtime/channel checks — **PASS**
`gateway/main.py:259-283`: the route reads `get_init_phase()` and `get_runtime()`, requires `phase == "ready"` AND `runtime is not None`, and additionally checks `any(a.is_connected for a in adapters.values())` when adapters exist. `_init_runtime()` (`main.py:104-156`) only sets phase to `"ready"` when `rt is not None` after `AgentRuntime.from_config()`/`.start()` succeed, else `"runtime_failed"` (line 156) — confirmed by grep that `set_init_phase("ready")` has exactly one call site in the whole repo, so nothing else can bypass this logic.

### 4.5 `_on_config_reload`'s `[security]` hot-reload — **PASS, but with a stale docstring nearby**
`gateway/main.py:65-91`'s `_on_config_reload` genuinely applies `POLICY.security`/`.ask` and calls `_set_live_require_shell_approval(...)` (`gateway/routes.py:2039-2051`, which mutates the live `ShellTool`/`BrowserAutomationTool` instances via `get_runtime()`'s tool registry) — a real, non-mocked live-path effect. It's invoked by `ConfigWatcher(cfg, on_reload=_on_config_reload)` at `main.py:93`, and `ConfigWatcher._watch()` (`config_watcher.py:77-102`) genuinely calls `await self._on_reload(fresh)` inside its real `awatch()` loop, confirmed by reading the whole watcher — this is a real filesystem-triggered callback, not a decorative one.

**Minor new finding**: `config_watcher.py`'s own module docstring (lines 1-11) is now stale — it claims the watcher applies "`[models]` — API keys and primary/fallback/fast model names" and "`[gateway].api_key`" on reload. Neither is true anymore: `_on_config_reload`'s own comment (`main.py:69-72`) explicitly states model/API-key hot-reload was *removed* rather than implemented, because `ModelRouter` has no live re-key path. This is a small, doc-only leftover from Round 4's own fix (the callback's behavior changed; the class docstring describing what any `on_reload` callback is expected to do was not updated to match). Low severity, easy one-line fix.

### 4.6 `neuralcleave approvals pending/approve/deny` gateway-proxy — **PASS**
`cli.py:2410-2452`'s `_gateway_url()`/`_try_gateway_json()` correctly resolve `cfg.gateway.bind`/`cfg.gateway.port` (mapping `0.0.0.0` → `127.0.0.1` for a connectable local address) rather than any hardcoded value, and all three commands (`approvals_pending`, `approvals_approve`, `approvals_deny` — `cli.py:2470-2553`) consistently call `_try_gateway_json()` first and fall back to the local in-memory queue only on connection failure, with real HTTP errors from a live gateway surfacing as `ClickException` rather than being swallowed. A repo-wide grep for the literal `7432` found one unrelated hardcoded fallback (`gateway/terminal.py:116-123`, `_gateway_base()`) that only activates when `load_config()` itself raises — a reasonable last-resort default, not a bug, and not part of the approvals path at all.

## 5. Newly identified gaps (fresh sweep)

Per the brief, this section covers subsystems no prior round's "newly identified gaps" section had named: `neuralcleave/memory/`, `neuralcleave/orchestrator/`, and `neuralcleave/hub/`. Voice pipeline wiring and the canvas/widget model were folded into §4.3 and §6 respectively rather than given fully separate dedicated sweeps, since real evidence surfaced there already. Desktop/Tauri sidecar spawn was not swept — the in-repo `frontend/src-tauri/` tree is almost entirely build artifacts, not source worth auditing from this repo alone.

### 5.1 Semantic memory is dead by default in every documented install path (headline finding)
`neuralcleave/memory/embedder.py:61-67` returns `None` and logs a warning whenever `sentence_transformers` fails to import. `pyproject.toml:23-43` (core `dependencies`) and lines 45-57 (`dev`/`voice` extras) — the actual PyPI packaging metadata every real install path uses — **never lists `sentence-transformers`**. `scripts/install.sh` and `README.md`'s Quick Start both document only `pip install neuralcleave` / `pip install -e ".[dev]"`. Only the separate, non-canonical `requirements.txt` includes it, and nothing in the README or `neuralcleave init` points a fresh user there. Traced through the live pipeline: `agent/pipeline.py:155-157` always computes `_embedding = await _embed(text)` → `None`; `MemoryRetrievalPipeline.retrieve()` skips its whole semantic-search branch whenever `embedding is None` (this holds true independent of whether Qdrant/Redis are configured — the fallback engineering there is solid but moot). `mintlify-docs/memory.mdx` compounds this by documenting a `[memory] backend/embedding_model/top_k/chunk_size` config surface and an `embeddings` extras group that don't exist anywhere in the real `MemoryConfig` (`config.py:56-62`) or `pyproject.toml`.
**Portability judgment**: trivial to fix (add the dependency, or a real extras group plus an init-time warning) but high-impact — this is a core "personal AI assistant" differentiator that is silently non-functional for essentially every real user today, not a config edge case.

### 5.2 Orchestrator subsystem is fully built but entirely disconnected from any real conversation
`orchestrator/orchestrator.py:165-193`'s `AgentOrchestrator.route()` — the only method that would actually dispatch a task to a node — is a documented stub by its own docstring's admission ("intentionally lightweight... returns a placeholder result") and its real return value is the hardcoded string `f"[routed to {node.name}]"`, never a model's actual output. The node-selection logic underneath (`can_handle`/priority/round-robin/keyword/channel matching) is genuinely real and well-tested, but it's never fed a task by any live conversation: `agent/pipeline.py` and `agent/runtime.py` contain zero references to `neuralcleave.orchestrator`. The gateway's live orchestrator (`gateway/main.py:117-125`, `AgentOrchestrator()`) boots with zero nodes and no config-driven way to pre-register any (`config.py` has zero `orchestrat*` fields) — the only way to populate it is a manual `POST /api/v1/orchestrator/nodes` call that doesn't survive a restart. The CLI `orchestrate` group (`cli.py:2072-2178`) makes it worse, not better: every subcommand constructs a fresh, throwaway `AgentOrchestrator()` in-process, with no persistence and no connection to the running gateway's instance at all — `orchestrate add` then `orchestrate list` in two separate invocations shows an empty list the second time.
**Portability judgment**: real and portable, but a meaningfully bigger lift than any single Round 4 item — closer to "finish building a subsystem" than "flip a switch." Selection logic and REST/CLI scaffolding already exist; what's missing is (a) actually invoking a node's model via `CognitivePipeline` from `route()`, (b) a real call site for it in the chat pipeline, and (c) either a config schema for startup node registration or a gateway-proxied CLI (reusing the exact pattern Round 4 §8 already built for `approvals`).

### 5.3 Hub marketplace installs silently never become callable tools
`gateway/main.py:145` constructs the live `HubInstaller(plugin_registry=plugin_registry)` — correctly passing the runtime's real `PluginRegistry` — but `HubInstaller.__init__` (`hub/installer.py:61-73`) only stores it as `self._plugin_registry`, which is **never read anywhere else in the class** (confirmed by grep: exactly one occurrence, the assignment). The actual registration step lives in `SkillWriter.write_skill()`, reachable only via `self._skill_writer` — which is never constructed from the injected `plugin_registry` (contrary to the class docstring's claim that a `SkillWriter` is "created fresh if not provided"; the real code just leaves it `None`). Since `main.py:145` never passes `skill_writer=`, every install — REST or CLI — falls into `_write_skill()`'s fallback branch (`installer.py:245-248`): raw code is written to disk and the function returns, with no module load and no `PluginRegistry`/`ToolRegistry` registration at all, and no directory-scan-on-startup exists to pick it up later. `cli.py:2274`'s `neuralcleave hub install` is worse still — it constructs a bare `HubInstaller()` with no registry wiring whatsoever, unlike the gateway-proxy pattern Round 4 §8 established for `approvals`. The in-repo `main.py:130-133` comment explicitly (and incorrectly) claims this exact wiring "is what actually lets hub-installed... tools reach the live agent."
**Portability judgment**: small, cheap fix (same shape as Round 4's own P0) — either have `HubInstaller.__init__` build a `SkillWriter(plugin_registry=self._plugin_registry)` internally when given a registry but no explicit writer, or have `main.py:145` construct and inject a real one. Also worth noting: the Hub has no remote/curated catalog at all today (`HubRegistry.search()` only searches already-installed local packages) — "marketplace" is currently an aspirational name for a URL-fetch-and-scan pipeline, a separate, lower-priority honesty gap from the wiring bug itself.

### 5.4 Memory auto-compaction and the heartbeat scheduler are both dead code
Two related, smaller findings from the same sweep:
- `memory/compactor.py:11,133`'s `maybe_compact()` docstring claims it's "called by the agent pipeline after every turn" — it is not. Grep confirms it's called only from its own definition and its own test file; `agent/pipeline.py`'s `run()`/`run_stream()` never call it. Only the manual `/compact` slash command reaches `compact()` directly. Same shape as the bug class from rounds 2-4.
- `gateway/main.py:61-63` constructs a `HeartbeatScheduler()` and starts it in every gateway boot, but `add_task()` — the only way to register a job with it — has **zero call sites anywhere in the app** outside `scheduler.py`'s own usage-example docstring (confirmed by grep). The entire cron/interval scheduling engine (real, well-built, and well-tested in isolation per `tests/unit/test_scheduler.py`) runs forever with an empty task dict in every live gateway today. `SessionArchiver` (the other candidate consumer) is constructed only inside the `neuralcleave memory archive` CLI command, never scheduled.
**Portability judgment**: both small fixes. Compaction: call `maybe_compact()` after Stage 6 in `pipeline.py`. Scheduler: register at least the memory-archival job as a real `ScheduledTask` at startup — or, if genuinely not a near-term priority, the honest move is to say so rather than let an entire "proactive assistant" subsystem run inert indefinitely.

## 6. Round-4 deferred items — concretely scoped

### 6.1 Capability-scoped widget/dashboard security model
NeuralCleave's canvas already has the *same baseline primitive* OpenClaw uses: `html` blocks render in `<iframe sandbox="allow-scripts">` (`canvas/routes.py:283`, confirmed — no `allow-same-origin`). What's missing is everything OpenClaw's now-detailed spec (`docs/web/dashboard-architecture.md`, read in full this round) builds on top of that: a per-widget capability manifest (`data` bindings, `actions` allowlist, `net` origin allowlist), byte-and-revision-bound grants, a `board_widgets` SQLite table, and a consent UI. OpenClaw itself scoped this as **six sequenced work branches** (T1-T7 in that doc) for a funded team — it is a genuinely large lift, not a quick win, confirming Round 3/4's call.

**Concretely missing today, confirmed by reading the render path**: there is no CSP applied to the `html` block's `srcdoc` at all (`canvas/routes.py:272-285`) — an agent-authored HTML block can `fetch()`/`XMLHttpRequest` to any origin today, unrestricted. This is the single biggest concrete risk in the current system and is fixable without the full manifest/grant machinery.

**Effort estimate**: Large (multi-week solo) for the full manifest + grant-consent system matching OpenClaw's spec. **Smallest defensible first slice** (Small, days not weeks): add a `Content-Security-Policy: default-src 'none'` (or a declared `connect-src` allowlist) into the rendered `srcdoc` for `html` blocks, defaulting to no network access unless a block explicitly declares allowed origins on a new `CanvasBlock` field. This establishes the enforcement primitive and closes the actual open risk without building the grant UI, revocation, or byte-freezing OpenClaw's full spec includes.

### 6.2 Secrets split (protected vs. agent-readable)
Round 4's summary of OpenClaw's commit `0d14434d0e8` (`feat(secrets): add explicit protected and agent-readable access (#126088)`, 2026-08-18) was slightly broader than the commit itself — read in full this round, it's primarily about the Codex sub-harness's dynamic-tool-build path and Gateway exec-alias policy binding (files touched: `docs/gateway/secrets.md`, `docs/plugins/codex-harness.md`, and the `codex/src/app-server/dynamic-tool-build.ts` pair), not a wholesale secrets-storage redesign.

NeuralCleave's actual position is better than Round 4's "worth a future look" framing suggested: `tools/shell.py:344-351`'s `_sanitize_env()` already strips environment variables matching sensitive patterns (`API_KEY`, `TOKEN`, `SECRET`, etc.) before every subprocess exec — a working, if heuristic, version of "protected." The real gap, confirmed by grep, is that **this filtering is `ShellTool`-only** — `tools/browser.py` has zero matches for `env=`/`os.environ`/`_sanitize_env`, meaning `BrowserAutomationTool` (which can also spawn processes/network contexts) has no equivalent scrubbing.

**Effort estimate**: Small. **Smallest defensible first slice**: extract `_sanitize_env()` into a shared helper (e.g. `tools/_env.py`) and apply it everywhere a tool inherits the parent process environment, starting with `BrowserAutomationTool`; make the sensitive-key pattern list configurable via `[security]` for anyone who wants a stricter or custom list. This is a real, cheap consistency fix — not the "future look" Round 4 filed it under, but also not the scale of the OpenClaw commit's actual scope.

### 6.3 Workboard-equivalent task board
Re-confirmed still **bundled but disabled by default** in OpenClaw (`docs/plugins/workboard.md:20`, verbatim). No new urgency — Round 3/4's deprioritization holds. Worth a one-line flag for future rounds: the feature itself has grown substantially since first flagged (20+ agent tools, a dispatch/worker-selection engine, session-lifecycle sync, three native session-board widget kinds) — if OpenClaw ever flips its default-enabled switch, the relative gap will be much larger than it was when Round 3 first noted it. Not a reason to build it now.

## 7. Recommended build order

Per the brief, genuinely broken/dead live-path wiring found in §4/§5 is prioritized over the already-known-heavy deferred items in §6 — a lot turned up, more than Round 4 found in its own re-verification pass.

### P0 — Make semantic memory actually work out of the box (§5.1)
Add `sentence-transformers` to `pyproject.toml`'s core `dependencies` (or, if the install-size cost is a concern, a real `embeddings` extra plus a loud `neuralcleave init`-time check/warning when it's missing) and correct `mintlify-docs/memory.mdx` to describe the actual `MemoryConfig` fields instead of a fictional `[memory]` schema. Highest priority: this is silently broken for every real user today, not an edge case, and directly undercuts the "semantic memory" pitch already used to justify shipping this feature in Round 2.

### P1 — Fix Hub install to actually register tools with the live agent (§5.3)
Inject a real `SkillWriter(plugin_registry=...)` into `HubInstaller` at its `gateway/main.py:145` construction site (or have `HubInstaller.__init__` build one internally when given a registry but no explicit writer), and route `neuralcleave hub install` through the same gateway-REST-proxy pattern Round 4 §8 already built for `approvals`. Cheap, and currently the Hub reports install success while doing nothing — a trust-damaging silent failure exactly like Round 4's own P0.

### P2 — Wire memory compaction and register at least one scheduler task (§5.4)
Call `maybe_compact()` after each turn in `agent/pipeline.py`, and register the existing `SessionArchiver`/memory-archival logic as a real `ScheduledTask` on the already-running `HeartbeatScheduler` instead of leaving it CLI-only. Bundling these is efficient since both live in the same area and both are the same bug shape.

### P3 — Extend `/think` to the streaming path (§4.3)
Thread a `thinking` parameter through `generate_stream()`/`_call_stream()` for the providers already wired in the non-streaming path (at minimum Claude and Ollama), closing the gap for NeuralCleave's own Web UI chat and voice assistant — currently the only two surfaces where `/think` silently does nothing.

### P4 — Orchestrator: cheap fix now, full wiring deferred
Given the effort/impact tradeoff, do the small piece now — proxy the CLI `orchestrate` group through the gateway's REST API (reusing the `approvals` pattern) and correct `route()`'s docstring/comments so they stop claiming behavior that doesn't exist — but explicitly defer actually wiring `route()` into a real `CognitivePipeline` call reachable from a live conversation (§5.2) to Round 6. That's a genuinely bigger, more architectural lift than P0-P3 and shouldn't be scoped under time pressure in the same PR as the others.

### Deliberately not prioritized this round
- **Capability-scoped widget/dashboard security model** (§6.1): the CSP default-deny slice is cheap and arguably should ride along with P3/P4 if there's room, but the full manifest+grant system remains a large, multi-week lift appropriately deferred.
- **Secrets split** (§6.2): the `BrowserAutomationTool` env-sanitization gap is real and cheap but lower-severity than P0-P4 — good Round 6 filler, not urgent now.
- **Workboard-equivalent task board** (§6.3): still correctly deprioritized, no new urgency.
- **Native mobile/desktop, browser extension, widget marketplace**: unchanged verdict from every prior round.

## 8. One-paragraph summary for future sessions

As of 2026-08-21 (same day as Round 4, hours later), Round 4's own three shipped fixes hold up under re-verification — the exec-approval on-switch, `/ready`'s runtime checks, and the CLI gateway-proxy pattern are all genuinely wired end-to-end — with one real depth gap found in the `/think` claim: it works for all 32 external channel adapters (which use the non-streaming `generate()` path) but is structurally absent from `generate_stream()`, meaning it silently does nothing for NeuralCleave's own Web UI chat and voice assistant. Far more significant was a first-ever fresh sweep of three previously-unaudited subsystems: the semantic memory pipeline is dead by default in every documented install path because `sentence-transformers` was never added to `pyproject.toml`'s packaged dependencies (§5.1, the headline finding — this silently guts a core assistant-pitch feature for essentially every real user); the orchestrator subsystem is fully built (real node-selection logic, REST/CLI surface) but its `route()` method is a documented stub returning a hardcoded placeholder string, never reached by any live conversation and never persisted across CLI invocations (§5.2); Hub-marketplace installs report success but never register with the live `ToolRegistry` because the injected `PluginRegistry` reference is silently unused (§5.3); and both memory auto-compaction and the entire heartbeat scheduler are dead code with zero real call sites outside their own docstrings and tests (§5.4). Round 4's deferred items (capability-scoped widgets, secrets split, Workboard) were concretely scoped rather than re-flagged: the widget model's smallest defensible slice is a default-deny CSP on canvas `html` blocks (currently unrestricted network egress, confirmed), the secrets split's real gap is that `BrowserAutomationTool` lacks the env-sanitization `ShellTool` already has, and Workboard remains correctly deprioritized. Round 5's build order leads with the fresh-sweep dead-wiring bugs in user-impact order — P0 semantic memory, P1 Hub install registration, P2 memory compaction + scheduler wiring, P3 streaming `/think`, P4 a cheap orchestrator CLI-proxy fix with full pipeline wiring explicitly deferred to Round 6 — deliberately ranking all of it above the heavier, already-well-understood deferred items from Round 4.

## 9. Implementation note — a fifth dead subsystem found while building P2, not yet fixed

While wiring auto-compaction (P2), tracing `/compact`'s actual call path turned up that `agent/runtime.py`'s slash-command handler does **not** delegate to `ConversationCompactor.compact()` at all — it has its own separate, duplicated inline summarization logic (`runtime.py`'s `_command_reply`, `cmd == "/compact"` branch). The *only* real caller of `ConversationCompactor` anywhere in the codebase is `neuralcleave/commands/handler.py`'s `CommandHandler` class — and `CommandHandler` itself is never constructed or imported anywhere outside its own module and three test files (`test_commands_handler.py`, `test_voice_commands.py`, `test_voice_listen_commands.py`), confirmed by a repo-wide grep. `neuralcleave/commands/` appears to be a complete, parallel, entirely orphaned slash-command implementation — not merely one dead method, but a whole unused subsystem sitting alongside the one that's actually wired.

**Not fixed this round** — this needs a real design decision before touching it (is `CommandHandler` meant to eventually *replace* `runtime.py`'s inline dispatch, in which case the fix is migrating callers over and deleting the duplicate logic; or is it legacy/superseded code, in which case the fix is deleting the whole `commands/` package and its tests) rather than a mechanical wiring fix like P0–P4 above. Flagging for Round 6: read `neuralcleave/commands/handler.py` in full, compare its command set against `agent/runtime.py`'s `_SLASH_COMMANDS`/`_command_reply`, and make the call.

**Resolved 2026-08-23 (PR #143):** made the call — `CommandHandler`'s command set (`/reset`, `/memory`, `/model`, `/status`, `/compact`, `/voice`, `/canvas`) was missing five commands `runtime.py`'s live version already had (`/think`, `/tag`, `/tags`, `/privacy`, `/forget`, plus `/help`), so migrating *to* it would mean rebuilding newer functionality for no benefit. Deleted the whole `commands/` package and its three orphaned test files. The one command unique to it, `/canvas` as a typed chat command, was never reachable in production either (`runtime.py`'s dispatcher never recognized it), so nothing working was removed — canvas remains fully controllable via the CLI, REST API, and the agent's own `CanvasTool`.
