## 1. Headline verdict

Two independent findings this round, neither where the brief's own hypothesis expected them:

1. **OpenClaw genuinely has not shipped new capability since Round 5's snapshot**, despite ~3,400 commits and ~9 calendar days passing. The diff of `CHANGELOG.md`'s `### Changes` section between Round 5's cited commit and current `HEAD` is **empty** — every one of those commits landed as `### Fixes` (narrow bug fixes, almost entirely Control UI/Android/browser-extension/channel-specific) or as internal refactors invisible to the changelog. 2. **A fresh sweep of NeuralCleave's own attack surface found something none of Rounds 2–5 looked at**: `gateway/terminal.py`'s embedded desktop terminal executes raw shell commands via `asyncio.create_subprocess_shell(cmd, env={**os.environ})` — the full, unsanitized process environment (including every configured provider API key), completely bypassing the exec-approval architecture Rounds 4–5 spent real effort building and re-verifying — and the WebSocket endpoint that exposes it has no origin check and does not honor `gateway.api_key` even when the operator has explicitly configured one. This is not a "unit-tested in isolation" bug like every prior round's finding; it's a live, reachable code path with no gate at all (§5.2).

Round 5's own four build-order fixes were re-verified end-to-end (not just spot-checked) and **all hold up** — semantic memory, Hub install registration, the orchestrator's real generation path, and the canvas CSP are each genuinely wired from real gateway startup through to the documented behavior, with correct attribute names, correct construction order, and no silent `None`-swallowing at the connection points. ## 5. Newly identified gaps (fresh sweep)

### 5.1 No provenance-tracked memory deletion — NeuralCleave's `/forget` is a blunt keyword grep, not a lineage-aware purge
`agent/runtime.py:1135-1141`: the entire `/forget` implementation is `Usage: /forget <keyword> — Delete long-term memory entries matching a keyword`, backed by a plain substring/keyword match against `self._long_term`. There is no concept anywhere in `neuralcleave/memory/` of which session, channel, or sender a given memory entry originated from, no admission policy to exclude a source from ingestion going forward, and no dry-run preview before deletion. OpenClaw's newly-documented (`docs/concepts/memory-provenance.md`) `memory forget --session/--participant/--hook-source --dry-run` does all three: it tracks per-entry origin (session ID, participant, hook source) at ingestion time, lets an operator preview exactly what a deletion would remove before committing, and supports an admission policy that keeps a specific channel/source out of memory ingestion entirely.
**Portability judgment**: real and directly relevant to NeuralCleave's own privacy pitch (it already ships a `PrivacyAuditLog` subsystem from Round 3, so privacy/trust is an established part of the product story) — a user who wants to remove everything a specific channel or contact ever caused the assistant to remember currently cannot do this at all, only a lucky keyword match. This is a genuinely bigger lift than a one-line fix (it requires threading a session/sender tag through every write path into long-term memory, not just the deletion command), but it is scoped and bounded, not an open-ended redesign — closer in size to Round 5's orchestrator wiring than to the full widget/dashboard system. Not urgent enough to jump ahead of §5.2, but a real, well-evidenced, previously-unflagged gap worth a build-order slot.

### 5.2 `gateway/terminal.py`'s embedded shell bypasses exec-approval entirely, and its WebSocket has no auth (headline finding)
`gateway/terminal.py:367-376`'s `_run_command()` executes arbitrary strings via `asyncio.create_subprocess_shell(cmd, stdout=..., stderr=..., env={**os.environ})` — the **full, unsanitized** process environment, not the `sanitize_env()` helper `tools/env_sanitize.py` provides and that `ShellTool`/`BrowserAutomationTool` were specifically fixed to use in PR #142 three commits ago in this same repo's history. This path is completely outside the `ApprovalQueue`/`POLICY.security`/`require_shell_approval` machinery Rounds 4–5 built and this round re-verified in §4 — there is no approval check, no `PrivacyAuditLog` entry, and no per-session identity check anywhere in the file (confirmed by reading it in full; zero occurrences of "approval" or "audit").

The module's own docstring claims this is safe because "the endpoint only accepts connections from the local gateway (127.0.0.1 / localhost / Tauri virtual host) — enforced at the CORS middleware level in main.py." Tracing this claim against the actual code shows it does not hold:
- Starlette's `CORSMiddleware` — the exact middleware `gateway/main.py:237-256` installs — does not apply to WebSocket connections at all; it only wraps `scope["type"] == "http"` and passes every other scope straight through unchecked. This is Starlette's own documented behavior, not a NeuralCleave-specific bug, but the docstring's claim that CORS enforces origin restriction on this WebSocket is simply incorrect.
- `gateway/main.py:258-273`'s optional `gateway.api_key` middleware — the only other auth mechanism in the file — explicitly special-cases WebSocket paths out of enforcement: `if path.startswith("/ws/"): return await call_next(request)`, with a comment explaining this was a deliberate choice ("WS upgrade ignores headers on most clients"), reasonable for the custom `X-API-Key` header (the browser `WebSocket` constructor cannot set arbitrary headers) but not for an `Origin` check, which browsers attach to every WebSocket handshake automatically and which `terminal_ws()` never reads.
- `terminal_ws()` itself (`gateway/terminal.py:308-311`) calls `await websocket.accept()` immediately with no header or query-parameter check of any kind.

Net effect: with the default config (`gateway.bind = "127.0.0.1"`, confirmed at `config.py:94`), any web page the user's browser loads — or any other local process — can open `ws://127.0.0.1:<port>/ws/terminal` and run arbitrary shell commands as the OS user running the gateway, with every configured provider API key present in the subprocess environment, and with zero record left in the audit log. This is a classic cross-site-WebSocket-hijacking-to-RCE shape, applied to a project whose exec-approval story is otherwise one of its more carefully built subsystems (per Rounds 3–5). The same WS-level auth gap exists in `gateway/websocket.py` (the main chat socket), but that path routes through the full `CognitivePipeline`/tool-approval stack before anything executes, so its blast radius is bounded by whatever tools are already gated; `terminal.py`'s is not bounded by anything.
**Portability judgment**: this is NeuralCleave's own code, not an OpenClaw comparison item, but it is exactly the kind of "claims vs. reality" gap this recurring exercise exists to catch, and it is cheap to fix: check `websocket.headers.get("origin")` against the same allow-list `CORSMiddleware` already declares before calling `.accept()` in both `terminal_ws()` and the main chat socket, and route `_run_command()`'s subprocess spawn through the existing `sanitize_env()` helper. No architectural change required.

### 5.3 Voice pipeline: the runtime wiring is genuinely solid; the *documented configuration surface* is not
Given the brief's specific suspicion about voice wiring, `agent/runtime.py`'s full wake-word → continuous-listener → STT → pipeline → TTS chain was traced end-to-end and found **correctly connected**: `AgentRuntime.start()` (`runtime.py:312-323`) starts both the wake detector and continuous listener and wires `self._continuous.on_transcription(self._on_voice_transcription)`; `_on_wake_word()` (`runtime.py:644-669`) pauses the wake detector, starts continuous listening for `wake_handoff_duration_s`, and `_revert_to_wake_mode()` (`runtime.py:671-692`) correctly reverts and resumes the detector afterward; `_on_voice_transcription()` (`runtime.py:440-475`) runs the real `process_inbound_text_stream()` pipeline and synthesizes + plays back the reply via TTS. No disconnected wire found in this chain — a genuine contrast with the pattern every prior round has found.

The real gap is one level up: **the documented TOML configuration keys for enabling voice features are wrong in three of the four voice doc pages**, and match neither `config.py`'s real `VoiceConfig` field names nor `configuration.mdx`'s own (correct) reference table. Confirmed:

| Doc file | Documented key | Real `config.py` field | Effect of following the doc |
|---|---|---|---|
| `mintlify-docs/voice/overview.mdx:35` (the "Quick enable" snippet) | `stt_backend = "whisper"` | `stt` (`config.py:67`) | Silently ignored — STT never enables |
| same snippet | `tts_backend = "kokoro"` | `tts_engine` (`config.py:72`) | Silently ignored — TTS never enables |
| same snippet | `wake_word_model = "alexa"` | `wake_word` (`config.py:76`) | Silently ignored — wake word never enables |
| `mintlify-docs/voice/wake-word.mdx:12-13` | `wake_word_model`, `wake_word_sensitivity` | `wake_word`, `wake_word_threshold` | Same — wake word never enables |
| `mintlify-docs/voice/push-to-talk.mdx:22` | `stt_backend = "whisper"`, claimed to auto-activate PTT | `stt` | PTT never activates; `ptt_stop_and_respond()` (`runtime.py:508`) hard-requires `self._stt is not None`, which requires the real `stt` key |

`mintlify-docs/configuration.mdx:99-109` has the correct field names (`wake_word`, `wake_word_model_path`, `wake_word_threshold`, `continuous_voice_enabled`, and elsewhere `stt`/`tts_engine`), so this is not a case of nobody knowing the real schema — the three task-oriented voice doc pages (overview, wake-word, push-to-talk) were simply never reconciled against it, the same failure mode Round 3's P9 docs pass found and fixed for a wrong port number across 19 files. A user who copies the most prominent, example-driven "Quick enable" snippet — the one actually meant to get someone started — configures nothing at all, with no error or warning anywhere in the chain (`config.py`'s loader uses `.get(key, default)` throughout, so an unrecognized key is silently dropped).

There is a second, smaller, related gap worth noting: even with the *correct* key `wake_word` set, `voice/wake-word.mdx`'s "Handoff" section describes an automatic, built-in handoff to VAD/STT with no mention that `continuous_voice_enabled` must **also** be set to `true` — but `agent/runtime.py:240-253` only constructs `self._continuous` when `cfg.voice.continuous_voice_enabled` is independently true, and `_on_wake_word()`'s handoff logic silently no-ops when `self._continuous is None` (`runtime.py:663`). So even a user who discovers the correct `wake_word` key from `configuration.mdx` and sets only that gets a wake-word detector that fires, logs, and increments a metric, but never actually listens to anything afterward, with no error indicating why.
**Portability judgment**: cheap, mechanical fix — correct the three doc pages' TOML key names to match `configuration.mdx`, and either document the `wake_word` + `continuous_voice_enabled` pairing requirement explicitly or (better, since it removes an easy-to-miss trap) make `AgentRuntime.from_config()` auto-enable continuous listening whenever `wake_word` is set and `continuous_voice_enabled` was left at its default. This is not a wiring bug in the sense every prior round found — the code paths are real and connected — but the practical effect for a real user following the docs is identical: the feature does not turn on.

## 6. Recommended build order

### P0 — Close the terminal WebSocket auth gap (§5.2)
Add an `Origin` header check against the same allow-list `CORSMiddleware` already declares (reject the WebSocket handshake in `terminal_ws()` before `.accept()` if `Origin` is missing or not in the allow-list) and route `_run_command()`'s subprocess spawn through `tools/env_sanitize.py`'s `sanitize_env()` instead of raw `os.environ`. Apply the same `Origin` check to `gateway/websocket.py`'s main chat socket while in the area, since it shares the identical unguarded-accept pattern even though its blast radius is smaller. Highest priority given this is a live, reachable, approval-free shell-execution path with secrets exposure, not a "unit-tested but unreached" bug — the severity class every prior round's headline finding has been building up to catching, finally found directly rather than through claim-vs-code tracing alone.

### P1 — Fix the voice docs' wrong TOML keys and the wake-word/continuous-listening pairing trap (§5.3)
Correct `voice/overview.mdx`, `voice/wake-word.mdx`, and `voice/push-to-talk.mdx` to use the real field names already correctly listed in `configuration.mdx` (`stt`, `tts_engine`, `wake_word`, `wake_word_threshold`). Separately, either document that `continuous_voice_enabled = true` is required alongside `wake_word`, or change `AgentRuntime.from_config()` to imply it automatically when a wake word is configured and the user never explicitly set `continuous_voice_enabled = false`. Cheap, mechanical, and directly blocks a real user from ever getting voice working via the docs as written today — the same severity class as Round 3's port-number doc bug.

### P2 — Session/source-scoped memory provenance and forgetting (§5.1)
Thread a session/sender tag through long-term memory's write path and extend `/forget` (and its REST/CLI equivalents) to select by that lineage rather than only a keyword substring, with a dry-run preview before deletion. Bigger than P0/P1 but bounded and directly reinforces NeuralCleave's existing privacy/trust positioning (`PrivacyAuditLog`, Round 3).

### Deliberately not prioritized this round
- **A2A channel** (§3): real, portable, reasonably scoped, but no signal of user demand and channel breadth was already settled as a non-gap in Round 3. Good future-round candidate if agent-to-agent interop becomes relevant.
- **Capability-scoped widget/dashboard security model**: unchanged — still correctly deferred as a large, multi-week lift; no new urgency signal found this round.
- **Workboard-equivalent task board**: unchanged — still opt-in/disabled by default in OpenClaw itself, no new urgency.
- **OpenClaw telemetry, triage CLI, IMAP isolated-reader automation**: all minor, none rise to build-order priority this round.
