## 1. Headline verdict

Three findings, in descending severity:

1. **Round 6's P2 fix does not reach the channel it was written for.** `agent/session.py:67` now derives `session_id` as `f"{channel}:{sender_id}"` — correct, and every downstream consumer traced clean. But the gateway's own WebSocket (`gateway/websocket.py`) constructs its per-connection `Session` dataclass with `session_id: str = field(default_factory=lambda: str(uuid.uuid4()))` (line 26) and then passes **that UUID as `sender_id`** into `process_inbound_text_stream()` at three separate call sites (lines 215, 337, 412). The agent-level session id for the desktop app and the web UI is therefore `websocket:<fresh-uuid4-per-connection>` — still random, still minted on every page reload, reconnect, or gateway restart. Long-term memory writes (`runtime.py:805`) and *retrieval* (`pipeline.py:171,269`) are both scoped by that id, so the primary UI still has no memory continuity across a single browser refresh. Round 6 correctly diagnosed the symptom and fixed the wrong layer (§4.3).
2. **The PWA mobile companion is a complete facade, and it is a load-bearing marketing claim.** `README.md:56` and `README.md:81` sell it as the answer to OpenClaw's native apps ("Mobile companion | Native apps | ✅ PWA from gateway — no app store"); `docs/COMPETITIVE_STRATEGY_2026_08.md:214` adds "receive push notifications" as a differentiator. In fact: the app shell's JavaScript speaks a protocol the server does not (it sends `{type:'message', content:…}` where `websocket.py:196` reads `text`/`payload`, and reads `msg.content` where the server sends `delta`), so every message typed into `/app` returns "⚠ Empty message"; the shell contains **no push-subscription code at all** (no `pushManager`, no `Notification.requestPermission`); `GET /api/v1/push/vapid-public-key` reads `app.state.vapid_public_key`, which nothing in `create_app()`/`_build_lifespan()` ever sets, so it returns 503 forever in production; and `POST /api/v1/push/notify` returns `{"sent": <subscriber count>}` while delivering nothing, its own comment conceding "Delivery requires pywebpush integration" (§5.1).
3. **Round 6's P0 origin check is 3-of-4 complete and introduced a self-inflicted regression.** `/ws`, `/ws/voice`, and `/ws/terminal` all consult `is_allowed_origin()` before `accept()`. `/ws/canvas` — a fourth WebSocket route, registered on `canvas_page_router` and included at `main.py:282` — calls `await ws.accept()` unconditionally at `canvas/routes.py:114` and immediately streams the full canvas state to the caller. Separately, the allow-list is built from `cfg.ui.web_port` (3000) and a regex that matches `localhost:<any port>` but **not** `127.0.0.1:<any port>`, while the gateway serves its own pages on `cfg.gateway.port` (7432) — so a user opening the gateway's own `/app` at `http://127.0.0.1:7432` now has their WebSocket closed with code 1008 (§4.1).

Round 6's other two deliverables — `terminal.py`'s `sanitize_env()` swap and the voice-docs TOML-key correction — re-verified clean (§4.2, §4.4). The `/forget` preview/confirm flow is real, reachable from both the streaming and non-streaming command paths, and is not dead code (§4.3).

## 4. Re-verification of Round 6's shipped fixes

### 4.1 P0 — WebSocket origin allow-list — **PARTIAL PASS, with a regression**

What holds up:
- `gateway/origin_check.py` exists and is genuinely populated in the real startup path: `main.py:245` calls `set_allowed_origins(cfg)` inside `create_app()`, *before* `add_middleware(CORSMiddleware, allow_origins=allowed_origins(cfg), …)` at line 254, so the module-level `_allowed` list is non-empty for every request the app can serve. This is not an importable-but-uncalled module.
- Three handlers consult it before `accept()`, verified by reading each: `websocket.py:116-119` (`/ws`), `websocket.py:449` (`/ws/voice`), `terminal.py:321-324` (`/ws/terminal`). All close with 1008 on mismatch.

**Gap A — a fourth WebSocket endpoint was missed entirely.** `canvas/routes.py:101` registers `@page_router.websocket("/ws/canvas")`, and `main.py:282` includes `canvas_page_router` in the app. Its handler (`canvas_routes.py:102-133`) calls `await ws.accept()` at line 114 with no origin check of any kind, then `await r.subscribe(ws)` — which immediately pushes the current canvas state (`{"type":"state","blocks":[…]}`) and every subsequent block the agent renders. Canvas blocks carry agent output: rendered tables, code, HTML, and whatever the assistant chose to display. So any page in the user's browser can silently subscribe to a live feed of the assistant's rendered output. This is a smaller blast radius than the terminal socket Round 6 fixed (it is read-only; client→server messages are explicitly ignored), but it is the same class of hole, in the same sweep, left open — and Round 6's own §5.2 resolution note claims all WebSocket handlers were covered.

**Gap B — the allow-list excludes the gateway's own origin (new regression).** `allowed_origins()` (`origin_check.py:46-56`) returns `http://localhost:{cfg.ui.web_port}`, `http://127.0.0.1:{cfg.ui.web_port}`, and the three Tauri hosts; `ORIGIN_REGEX` (line 41) is `https?://(tauri\.)?localhost(:\d+)?`. Defaults are `ui.web_port = 3000` (`config.py:116`) and `gateway.port = 7432` (`config.py:93`). The gateway serves its own HTML pages — the PWA shell at `/app` (`main.py:283`) and the canvas page — on **7432**. Therefore:

| Origin a browser will actually send | `is_allowed_origin()` | Why |
|---|---|---|
| `http://localhost:3000` (Next.js dev UI) | allowed | explicit list entry |
| `http://localhost:7432` (gateway page via localhost) | allowed | matched by `ORIGIN_REGEX` (any port) |
| `http://127.0.0.1:7432` (gateway page via loopback IP) | **rejected** | not in list (list only has 127.0.0.1:3000), and the regex has no `127.0.0.1` branch |
| `http://192.168.x.x:7432` (phone on the LAN, the PWA's whole purpose) | **rejected** | neither |

`127.0.0.1` and `localhost` are used interchangeably everywhere else in this project — `config.py:94` binds `127.0.0.1`, the CLI prints `{bind}:{port}` — so a user reaching the gateway's own page at the address the gateway itself printed gets a WebSocket that closes with 1008 and a UI stuck on "Reconnecting…", with no diagnostic anywhere. Before Round 6's fix that connection worked. The fix is one line (add the gateway port's own two origins, and a `127\.0\.0\.1` branch to the regex), but it is a genuine behavioral regression shipped as a security fix.

**Resolved (2026-08-30), both gaps**: `canvas/routes.py`'s `canvas_websocket()` now runs the same `is_allowed_origin()` pre-`accept()` check as the other three sockets (with matching-origin/mismatched-origin/missing-origin tests mirroring the existing pattern). `ORIGIN_REGEX` now matches `(localhost|127\.0\.0\.1)` instead of only `localhost`, closing gap B for any port on either host. The LAN-IP case (`192.168.x.x`) is deliberately still rejected — that's correct behavior, not a bug, until the PWA's own LAN-reachability problem (see §5.1's resolution note) is actually solved; a regex that accepted arbitrary LAN IPs would defeat the whole point of this allow-list.

**Also still open (not a regression — the untouched half of Round 6's own finding).** Round 6 §5.2 documented two problems with `terminal.py`: unsanitized env + no auth (both fixed), *and* that the endpoint "is completely outside the `ApprovalQueue`/`POLICY.security`/`require_shell_approval` machinery … no approval check, no `PrivacyAuditLog` entry." That half was never addressed and is not mentioned in the resolution note. Confirmed by grep over the current file: zero occurrences of `approval`, `audit`, `AUDIT`, or `POLICY` in `gateway/terminal.py`. A command typed into the desktop terminal still executes with no approval prompt and leaves no audit record, even with `security.require_shell_approval = true` — while the identical command issued by the *agent* through `ShellTool` is gated. See §6 P4.

### 4.3 P2 — `Session.session_id` + `/forget` — **PARTIAL PASS (headline finding)**

`/forget` — **PASS, real, not dead code.** `runtime.py:1135-1172` implements the preview/confirm split: a bare `/forget <keyword>` runs `long_term.search(session_id=…, query=keyword, limit=50)` and returns a count plus up to 5 truncated snippets and the literal instruction to reply `/forget <keyword> confirm`; only the `confirm` suffix loops `delete_entry()`. Reachability traced both ways: `/forget` is in `_SLASH_COMMANDS` (`runtime.py:52`), which is consulted by `_reply_for()` (`runtime.py:828-834`, the adapter/`process_inbound_text` path) **and** by `process_inbound_text_stream()` (`runtime.py:749-761`, the WebSocket path, which yields the command reply as a single `done=True` chunk). Both reach `_command_reply()`. `/help`'s text was updated to match. No dead code here.

`Session.session_id` — **correct in `session.py`, defeated one layer up.** The dataclass change is real (`session.py:67`), and downstream consumers were traced individually with no regression found:
- `SessionManager.get_by_id()` (`session.py:168-175`) does a linear scan comparing `session.session_id`, format-agnostic — the approval-routing path (`runtime.py:919`, `_handle_new_approval_request`) works unchanged, and the `ApprovalRequest.session_id` it matches against is fed from `pipeline.py:584`'s `session_id=session_id or ""`, i.e. the same derived string.
- The REST routes that take a session id in the path (`routes.py:296` `/agent/sessions/{session_id}/history`, `routes.py:330` `.../reset`) look it up by the same scan (`routes.py:315,347`) with no UUID parsing or format assumption. A colon in a path segment is legal and needs no escaping, so `GET /api/v1/agent/sessions/telegram:12345/history` resolves.
- `routes.py:250`'s `DELETE /sessions/{session_id}` operates on the **WebSocket** manager's dict, whose keys are still UUIDs — a different, untouched namespace, not a regression.
- One cosmetic leftover: `session.py:169`'s docstring still calls the value "the UUID", and `__repr__` (line 141) still truncates it to `session_id[:8]`, which for `"cli:user"` now prints a meaningless prefix. Neither affects behavior.

**But the fix never reaches the web/desktop channel.** `gateway/websocket.py:26` gives its own per-connection `Session` dataclass `session_id: str = field(default_factory=lambda: str(uuid.uuid4()))`, and all three chat entry points pass that UUID in as the *sender*:

| Call site | Channel | `sender_id` passed |
|---|---|---|
| `websocket.py:213-217` (text chat) | `"websocket"` | `session.session_id` (per-connection uuid4) |
| `websocket.py:335-339` (binary audio frame → STT) | `"websocket"` | same |
| `websocket.py:410-414` (`/ws/voice` stream) | `"voice_ws"` | same |

`runtime.py:763` then does `self._sessions.get_or_create(msg.channel, msg.sender_id)`, producing `session_id = "websocket:<uuid4>"`. `runtime.py:805` stores the exchange under it; `pipeline.py:171` and `:269` **retrieve** under it. Net effect, unchanged from before PR #145 for this channel: refresh the page and the assistant has forgotten everything; `/forget` and `/tags` see only the current connection's writes; every reconnect leaves another orphaned scope in `long_term`'s SQLite table. Round 6's own words — "a gateway restart or a single 30-minute idle gap silently orphaned a real user's entire memory history" — remain literally true for the desktop app and web UI, which is where a personal assistant's users actually are. The adapter channels (Telegram, Discord, …) *are* fixed, because they pass real platform sender ids; so are the local voice paths, which pass the stable literals `"local_mic"` (`runtime.py:454`) and `"local_ptt"` (`runtime.py:521`).

A second-order consequence worth noting: because the text socket uses channel `"websocket"` and the voice socket uses `"voice_ws"`, typed and spoken turns from the *same* UI land in two different memory scopes even within one connection.

**Resolved (2026-08-30)**: `gateway/websocket.py`'s `Session` dataclass gained a second field, `sender_id`, distinct from the pre-existing `session_id` (which stays a random per-connection ID for `WebSocketManager` bookkeeping — deliberately not repurposed). A new `_resolve_sender_id()` reads an optional `client_id` query param (validated against `[A-Za-z0-9_-]{1,128}`) and falls back to a fresh `uuid4()` — identical to the pre-fix behavior — when absent. All three call sites (`websocket.py:213-217`, `:335-339`, `:410-414`) now pass `sender_id=session.sender_id`. The frontend's `ReconnectingWSClient` (used by both `/ws` and `/ws/voice`) generates a client ID once via `crypto.randomUUID()`, persists it in `localStorage`, and sends it as `client_id` on every connect — so the same browser now keeps the same long-term-memory identity across reconnects. The second-order channel-split issue noted above (`"websocket"` vs `"voice_ws"`) is unchanged and not addressed by this fix — flagging for a future round.

### 5.1 The PWA mobile companion cannot chat, cannot subscribe, and cannot notify — while being pitched as a differentiator (headline finding)

`neuralcleave/pwa/` is 692 lines across three files, fully unit-tested (`tests/unit/test_pwa_routes.py`, `tests/unit/test_pwa_push.py`), wired into the real app (`main.py:283-284` includes both `pwa_router` and `push_router`), and advertised in `README.md:56` ("installable on iOS + Android from the gateway's own `/app` endpoint, no app store needed"), `README.md:81` (the head-to-head comparison table row against OpenClaw's native apps), `README.md:489` ("Push (PWA) | 5 endpoints"), and `docs/COMPETITIVE_STRATEGY_2026_08.md:214` ("receive push notifications. OpenClaw's Control UI is a standard web app, not a PWA"). Four independent breakages, each confirmed by reading both sides of the interface:

**(a) The app shell speaks a protocol the server does not.** `pwa/routes.py:297` sends `ws.send(JSON.stringify({ type: 'message', content: text, session_id: sessionId }))`. The server's `_handle_chat_message()` reads `text = (msg.get("text") or msg.get("payload") or "").strip()` (`websocket.py:196`) — `content` is not consulted — and on empty text replies `{"type":"error","message":"Empty message"}` (line 198). The shell renders that as "⚠ Empty message" (line 261). **Every message sent from `/app` fails.** The same mismatch exists on the return leg: the shell accumulates `msg.content` on `message_chunk` frames (line 251), but the server sends the increment as `delta` (`websocket.py:237`), so even a fixed send path would stream empty strings. This is not ambiguity about an evolving protocol — the real Next.js frontend gets it right (`frontend/src/app/(dashboard)/chat/page.tsx:648` sends `{type:"message", id, text}`, and line 561 reads `msg.delta`), which is exactly why nobody noticed: the PWA shell is a second, hand-maintained client that no test exercises against the real server.

**(b) There is no push-subscription client.** The service worker (`pwa/routes.py:72-96`) correctly handles `push` and `notificationclick` events, but the app shell's JavaScript (lines 186-313) contains no `Notification.requestPermission()`, no `registration.pushManager.subscribe()`, and no call to `POST /api/v1/push/subscribe`. Nothing in the shipped product can ever create a subscription; `/push/subscribe` is reachable only by hand-written curl.

**(c) The VAPID key endpoint is permanently 503 in production.** `pwa/routes.py:361-367` returns `app.state.vapid_public_key` or raises 503. That attribute is set in exactly one place in the entire repo: `tests/unit/test_pwa_routes.py:198`. Neither `create_app()` nor `_build_lifespan()` sets it, and `generate_vapid_keys()` (`pwa/push.py:139`) has **zero production callers** — grep across the repo finds it only in `pwa/push.py` itself and `tests/unit/test_pwa_push.py`. So even a hand-written client cannot obtain the `applicationServerKey` that `pushManager.subscribe()` requires.

**(d) `/push/notify` reports success while sending nothing.** `pwa/routes.py:420-443` builds a JSON payload, never transmits it, and returns `{"sent": len(subs), "payload_size": …, "note": "Delivery requires pywebpush integration"}`. `pywebpush` appears nowhere in `pyproject.toml` or any source file. An operator or a future scheduler task reading `sent: 3` would reasonably conclude three devices were notified.

**And even with (a)–(d) fixed, the stated use case still would not work today.** `gateway.bind` defaults to `127.0.0.1` (`config.py:94`), so a phone cannot reach `/app` at all without an explicit rebind; and if the operator does bind `0.0.0.0`, the phone's `Origin` (`http://192.168.x.x:7432`) is rejected by §4.1's allow-list, closing the WebSocket with 1008. On top of that, service workers, `Notification`, and the Push API are all secure-context-only in every modern browser, so a plain-`http` LAN origin cannot register the service worker the whole feature is built on. The "installable on iOS + Android" claim needs HTTPS termination that this project neither ships nor documents.

**Resolved (2026-08-30), minimal-fix + honest-docs path chosen over the full build**: (a) fixed on both legs — the shell now sends `{type: 'message', text: text, ...}`, and its receive handler now reads `msg.delta` for `message_chunk` and `msg.text` for `message_done`/`message`, matching the real frontend's protocol exactly. (d) fixed by making `/push/notify` honestly report `sent: 0, delivered: false` plus a separate `matched_subscribers` count, instead of a `sent` count that reads as delivery confirmation. (b) the missing push-subscription client, (c) the permanently-503 VAPID endpoint, and the deeper LAN-reachability problem (bind default + origin allow-list + secure-context requirement, all three independent of each other) remain **unaddressed** — this was an explicit scope decision (chat should work; push notifications were not rebuilt), not an oversight. The `README.md:56/81` "installable on iOS + Android" claim was left as-is rather than corrected in this pass — with (a) fixed, installing from the *same machine* the gateway runs on is now honest, but the phone/LAN scenario the claim implies is still blocked by the reachability problem above and was not evaluated as part of this fix; a future round should decide whether to soften that claim or actually solve LAN reachability (HTTPS + origin allow-list changes + a documented `gateway.bind` override).

**Portability judgment**: this is NeuralCleave's own code and the most complete instance yet of this project's signature bug class — built, unit-tested in isolation, wired into the router, documented as a competitive advantage, and non-functional end-to-end on four independent axes. The honest options are (i) fix it properly — one shared WS protocol constant between the two clients, a subscribe flow in the shell, VAPID keys generated once at startup and persisted to config, `pywebpush` as a real dependency, and documented HTTPS/reverse-proxy guidance — or (ii) mark `/app` experimental, make `/push/notify` return 501, and remove the competitive claims from `README.md` and the strategy doc. What is not defensible is leaving a comparison-table row that promises something no user can obtain.

### 5.2 The config hot-reload watcher watches a file it re-guesses, not the file the gateway loaded

`ConfigWatcher` is constructed at `main.py:98` with the live `cfg` object and started immediately, so the subsystem itself is genuinely wired (unlike, say, the scheduler before Round 5). The defect is in how it finds the file to watch: `_config_path()` (`config_watcher.py:104-113`) ignores the config entirely and returns the first of two hard-coded candidates that exists — `~/.neuralcleave/config.toml`, then `./config.toml`. A `NeuralCleaveConfig` carries no record of where it was loaded from, and the watcher never receives the path.

But `create_app(config=cfg)` is routinely called with a config loaded from somewhere else: `cli.py:130-135`'s `start` command does `cfg = load_config(ctx.obj.get("config_path"))`, where `config_path` comes from the global `--config/-c` option (`cli.py:76`), and passes the resulting object down. Two concrete failure modes follow, both verified by reading the code rather than inferred:

- **Wrong-file reload.** With `neuralcleave -c /work/staging.toml start` and a `~/.neuralcleave/config.toml` also present, the gateway runs on `staging.toml` while the watcher watches the home file. Any save to the home file fires `load_config(<home file>)` and hands the result to `_on_config_reload` (`main.py:70-96`), which applies `fresh_cfg.security.*` to the live `POLICY` and calls `_set_live_require_shell_approval(...)`. If the home file omits `[security]` (defaults: `require_shell_approval = False`), **editing an unrelated config file silently disables the exec-approval gate on a running gateway** — the precise gate Round 4's P0 was written to give an on-switch to.
- **Silent no-op.** With `-c` pointing at a file elsewhere and neither candidate present, `_config_path()` returns `None` and `_watch()` logs at DEBUG and returns. Hot-reload is off, and the only trace is a DEBUG line.

Neither case produces a warning at the level an operator would see. The fix is small and self-contained: thread the resolved path (`load_config` already computes it at `config.py:207`) onto the config object or into `ConfigWatcher.__init__`, and watch that.

A related, lower-severity observation from the same sweep: **`watchfiles` is not a declared dependency.** It appears nowhere in `pyproject.toml` — not in `dependencies`, not in the `dev` or `voice` extras — yet `config_watcher.py:79` imports it and disables hot-reload on `ImportError`. It happens to be installed in practice (confirmed present, 1.2.0) because `uvicorn[standard]` (`pyproject.toml:25`) pulls it in transitively. So this is not today's dead-by-default repeat of Round 5's `sentence-transformers` finding — but the entire hot-reload feature, including the live security toggle, rests on an undeclared transitive dependency that a future `uvicorn` extras change would remove without a single failing test. It should be declared explicitly. (`cryptography`, which `pwa/push.py:148` needs for VAPID generation, is in the same undeclared-but-transitively-present position.)

### 5.3 Hub installer: `http://` accepted despite an https-only contract, no host allow-list, and a checksum that verifies nothing

`HubInstaller._fetch_code()` (`installer.py:202-220`) branches on `source_url.startswith(("http://", "https://"))` — **cleartext `http://` is accepted** — while the method's own error message on the fall-through path says "Supported: `https://`, `data:text/plain,…`" (line 219) and the class docstring says the same (line 32). The fetched string then goes to `PackageScanner`, is written to `~/.neuralcleave/hub/skills/<name>/skill.py`, and is loaded and registered as a live, LLM-callable tool via `SkillWriter.write_skill()` (`installer.py:263`). So the one transport the code actually permits beyond the documented set is the one that lets a network-position attacker substitute the code that gets executed.

Two smaller issues in the same path: there is no host allow-list or redirect restriction (`follow_redirects=True` at line 210, so an allowed host can bounce the fetch anywhere), and the SHA-256 at `installer.py:145` is computed *from the bytes just fetched* and recorded in the registry — it documents what was installed but cannot verify it against a publisher-declared digest, because `install()` accepts no expected checksum. The `PackageScanner` AST/pattern scan and `SkillWriter`'s non-negotiable blocked-import check (documented at `installer.py:245-261`) are real mitigations and were re-read to confirm `force=True` cannot bypass the latter — this is a hardening gap, not an open door.

Also noted while tracing: `HubInstaller.scan_url()` (`installer.py:188-196`) has **zero callers anywhere in the repo, including tests**, and its implementation (`asyncio.get_event_loop().run_until_complete(...)`) would raise if called from any async context and is deprecated in 3.12+. Dead code; removing it is strictly cheaper than fixing it.

## 6. Recommended build order

### P0 — Finish Round 6's origin check, and fix the origin it broke (§4.1)
Two changes in `gateway/origin_check.py` plus one in `canvas/routes.py`. (1) Add `is_allowed_origin(ws.headers.get("origin"))` before `await ws.accept()` in `canvas_websocket()`, matching the three handlers already doing it — `/ws/canvas` streams live agent output to any origin today. (2) Add the gateway's own origins to `allowed_origins()` (`http://localhost:{cfg.gateway.port}` and `http://127.0.0.1:{cfg.gateway.port}`) and extend `ORIGIN_REGEX` to cover `127\.0\.0\.1` alongside `localhost`, so a user visiting the gateway's own page at the loopback address the gateway itself prints is not rejected. Highest priority because half of it is an open hole in a fix already declared complete, and the other half is a regression this project shipped one day ago. Add a test that enumerates every `app.routes` entry of type `WebSocketRoute` and asserts each handler rejects a mismatched origin — a per-endpoint test cannot catch the *next* missed endpoint.

**Resolved (2026-08-30)** — see §4.1's resolution note. The route-enumeration test suggested above was not added in this pass (the three explicit per-endpoint test suites were extended instead) — worth reconsidering for a future round if a fifth WebSocket ever gets added.

### P1 — Make Round 6's `session_id` fix actually reach the web/desktop channel (§4.3)
`gateway/websocket.py` must stop passing a per-connection `uuid4()` as `sender_id`. The minimum viable fix is a stable client identity: have the browser/desktop client persist an opaque id (localStorage / Tauri store) and send it in the `hello`/`subscribe` handshake, falling back to a per-install id the gateway persists in `~/.neuralcleave/`. Then pass *that* as `sender_id` at all three call sites (`websocket.py:215, 337, 412`), and use one channel name for both the typed and spoken paths of the same UI so a conversation is not split across two memory scopes. Without this, the desktop app and web UI still have no long-term memory across a page refresh — which is the user-visible symptom Round 6 set out to fix, and the single most valuable thing to close this round.

**Resolved (2026-08-30)**, the client-identity half — see §4.3's resolution note. The channel-split half (`"websocket"` vs `"voice_ws"`) was deliberately left open — unifying it touches how typed vs. spoken turns get scoped and felt like a separate decision from "does memory survive a reconnect," not a mechanical follow-on.

### P2 — Decide the PWA's fate: wire it or retire the claim (§5.1)
Either (a) fix it end-to-end — align the shell's WS protocol with the server's (`text` out, `delta` in; ideally extract one shared protocol description rather than two hand-maintained clients), add the permission + `pushManager.subscribe()` + `POST /push/subscribe` flow to the shell, generate VAPID keys once at startup and persist them into config, add `pywebpush` as a real dependency and make `/push/notify` actually deliver, and document the HTTPS/reverse-proxy requirement that installability and push both depend on — or (b) mark `/app` experimental, return 501 from `/push/notify`, and remove the mobile/push rows from `README.md:56,81` and `docs/COMPETITIVE_STRATEGY_2026_08.md:214`. Ranked below P0/P1 only because it is a larger, more discretionary piece of work; as a *claims-vs-reality* problem it is the worst thing in this document. Whichever branch is taken, add one integration test that drives the shipped `/app` JavaScript's exact message shape through the real `/ws` handler — the class of test whose absence let this survive.

**Resolved (2026-08-30) — a third path, chosen over both (a) and (b)**: neither the full build nor a full retire. Fixed (a)'s protocol mismatch on both legs (chat now genuinely works from `/app`) and (d)'s fabricated `sent` count — see §5.1's resolution note — but left (b) (no subscription client), (c) (503 VAPID endpoint), and the README's phone/LAN installability claim untouched. The suggested integration test (drive the shipped shell JS through the real `/ws` handler) was added in spirit via `TestPwaShell`'s new field-name assertions, though those check the served HTML source rather than executing the JS against a live handler — a real end-to-end browser-level test remains a good future addition.

### P3 — Bind the config watcher to the file that was actually loaded (§5.2)
Thread the resolved config path from `load_config()` through to `ConfigWatcher` instead of re-guessing it from two hard-coded candidates. Small, but it currently allows a save to an unrelated `~/.neuralcleave/config.toml` to apply *that* file's `[security]` defaults over a gateway started with `-c other.toml` — silently switching off `require_shell_approval` on a live gateway. While in the area, declare `watchfiles` (and `cryptography`) explicitly in `pyproject.toml` rather than relying on `uvicorn[standard]`'s transitive graph.

### P4 — Route the embedded terminal through exec-approval and the audit log (§4.1, still-open half of Round 6's P0)
`gateway/terminal.py` still contains no reference to `ApprovalQueue`, `POLICY`, or `PrivacyAuditLog`. With `security.require_shell_approval = true`, an agent-issued `rm -rf` is gated while the same command typed into the desktop terminal is not, and neither leaves an audit entry. Round 6 fixed this endpoint's transport auth and its secrets leak but explicitly described this third problem and then did not address it in the resolution note. Deferred to P4 rather than P0 because it is a real design decision (an operator typing into their own terminal arguably should not be prompted) — but the decision should be made and written down, and the audit-log entry should exist either way.

### Deliberately not prioritized this round
- **Hub `http://` fetch hardening and dead `scan_url()`** (§5.3): real but narrow — restrict `_fetch_code` to `https://`/`data:` as documented, accept an optional expected checksum, and delete `scan_url()`. A good drive-by for whichever PR next touches `neuralcleave/hub/`.
- **Memory provenance beyond `(channel, sender_id)`** (§3): cross-channel identity linking, hook-source attribution, and an ingestion admission policy remain unbuilt. The `session_id` fix delivered the per-participant-per-channel and dry-run halves; the rest is a genuinely larger design question and there is still no user-demand signal.
- **A2A channel**: unchanged from Round 6 — real and portable, no demand signal, channel breadth settled as a non-gap in Round 3.
- **Capability-scoped widget/dashboard security model** and **Workboard-equivalent task board**: unchanged; upstream produced zero commits this round, so neither gained urgency by definition.

## 7. One-paragraph summary for future sessions

As of 2026-08-30, OpenClaw's clone was re-fetched from its remote and `origin/main` is byte-identical to Round 6's snapshot (`4f3d6af7352a`) — zero upstream commits, so every finding this round is NeuralCleave's own. Re-verifying PR #145 produced the worst result since Round 4: the voice-docs key fix and `terminal.py`'s `sanitize_env()` swap both PASS cleanly, and the `/forget` preview/confirm flow is real and reachable from both the streaming and non-streaming command paths, but the other two are only partial. The WebSocket origin check is genuinely populated in `create_app()` and consulted by `/ws`, `/ws/voice`, and `/ws/terminal` — yet it misses a fourth endpoint nobody counted, `/ws/canvas` (`canvas/routes.py:114` accepts unconditionally and streams live agent output to any origin), and its allow-list is built from `ui.web_port` with a regex covering `localhost` but not `127.0.0.1`, so the gateway's own pages served on `gateway.port` are now rejected with close code 1008 when reached at `http://127.0.0.1:7432` — a regression introduced by the fix itself. More importantly, the deterministic `Session.session_id` fix is correct in `agent/session.py:67` and clean across every downstream consumer traced (approval routing, the REST `/agent/sessions/{id}` routes, `get_by_id`), but never takes effect on the primary channel: `gateway/websocket.py:26` still mints a `uuid4()` per connection and passes it as `sender_id` at lines 215, 337, and 412, so the desktop app and web UI still write and retrieve long-term memory under `websocket:<random>` and still forget everything on a page refresh — Round 6 fixed the layer below the bug. The fresh sweep of three never-audited subsystems found the PWA mobile companion (`neuralcleave/pwa/`, wired into the app at `main.py:283-284`, unit-tested, and sold in `README.md:81`'s head-to-head table against OpenClaw's native apps) to be a four-way facade: its shell sends `content` where the server reads `text` and reads `content` where the server sends `delta` (so every message returns "Empty message"), it contains no push-subscription code at all, `app.state.vapid_public_key` is set only in a test so `/push/vapid-public-key` is permanently 503, and `/push/notify` returns a `sent` count while delivering nothing — plus the default `127.0.0.1` bind, the origin allow-list, and the secure-context requirement each independently block the phone use case it advertises. Also found: `ConfigWatcher` re-guesses which config file to watch instead of using the one `load_config()` actually read, so with `neuralcleave -c custom.toml start` a save to an unrelated `~/.neuralcleave/config.toml` can silently switch off `require_shell_approval` on a live gateway; and the Hub installer accepts cleartext `http://` for remote code it will execute, despite its own docstring and error message promising https-only. Build order: P0 finish the origin check (`/ws/canvas` + the gateway's own origins, with a route-enumerating test so the next endpoint can't be missed), P1 give the WebSocket a stable client identity so Round 6's memory fix reaches the desktop UI, P2 either wire the PWA end-to-end or retire its README claims, P3 bind the config watcher to the real config path, P4 decide and document whether the embedded terminal should honor exec-approval and must at minimum write an audit entry.
